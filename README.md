## 실습과 결과 기록

- **구현 범위**　각 과제의 동작과 실패 시 결과가 요구사항이다. 클래스 이름, 함수 이름, 파일 구성, 콘솔 입력 방식은 직접 정한다. 먼저 코드에 고정한 작은 입력으로 시작해도 된다.
- **검증**　입력마다 기대값을 먼저 적고 실행 결과와 대조한다. 무한 대기 가능성이 있는 테스트는 별도 프로세스로 실행하고 제한 시간(예시 10초)을 둔다. 시간 초과는 조사할 실패로 기록한다. 반복 실행의 성공만으로 경쟁 상태나 기아 가능성을 배제할 수는 없다.
- **측정**　아래 수치는 바로 시작할 수 있는 기본 실험 조건이다. 너무 짧거나 오래 걸리면 작업량을 조절하고 변경값을 기록한다. 같은 기기·Release 빌드·입력으로 조건당 예열 1회 후 5회 측정한다. 원시값을 보관하고 대표값으로 중앙값을 쓴다. 기본 측정 구간은 준비된 작업자에게 시작 신호를 보낸 때부터 마지막 작업자가 일을 마친 때까지다. 파일 쓰기가 과제 자체인 P11은 파일 닫기까지 포함한다.
- **지표**　경과 시간은 `steady_clock`으로 잰다. 처리량은 완료한 작업 수를 경과 초로 나눈 값이다. 대기 시간은 요청 직전부터 자원을 얻은 직후까지다. p95는 표본을 정렬했을 때 약 95%가 그 값 이하인 지점이다. 대기 표본은 작업자별로 모아 종료 후 합친다. 콘솔 출력과 정답 대조는 측정 구간 밖에서 한다.
- **제출 기록**　과제별로 CPU·논리 프로세서 수·컴파일러·빌드 설정, 테스트 입력과 기대값/실제값, 측정표, 결과를 설명하는 한두 문장을 남긴다. 특정 구현의 승리나 속도 향상률은 합격 조건에 포함하지 않는다.

## P01 · 멀티스레드 카운터

작업자 2명이 각각 3번씩 카운터를 올린다. 둘이 어떤 순서로 실행되든 마지막 출력은 6이어야 한다.

**만들 기능**　작업자 수 N과 1인당 증가 횟수 R을 받는다. 순차 실행, 공유 정수를 mutex로 보호하는 실행, atomic 정수를 증가시키는 실행을 만든다. 매번 0에서 시작하고 결과에는 충분히 큰 정수형을 쓴다.

### 구현 순서

1. 한 스레드로 N × R번 증가시켜 기준값을 만든다.
2. N개 작업자가 같은 카운터에 접근하게 하고, 모든 작업자를 join한 뒤 최종값을 읽는다. mutex 버전과 atomic 버전에 같은 입력을 준다.
3. 학습용 별도 실행 파일에 잠금 없는 공유 정수 증가를 둔다. 데이터 레이스는 미정의 동작이다. 지원 환경에서는 ThreadSanitizer(TSan)로 이 예제와 수정본의 진단을 비교한다.

### 검증

- N=2, R=3이면 세 정상 구현 모두 6, R=0이면 0이어야 한다.
- N=1/2/4/8, R=100,000으로 반복해 기대값과 실제값을 기록한다. 레이스 예제가 우연히 기대값을 출력해도 정상 구현으로 채점하지 않는다.

### 벤치마크

같은 N과 R에서 세 정상 구현의 시간과 초당 증가 횟수를 기록한다. N이 달라지면 총작업량도 달라진다는 점을 표에 표시한다.

**완료 기준**　모든 정상 실행에서 기대값이 일치하고 작업자가 종료된다. join의 역할과 공유 정수 증가에 잠금이 필요한 이유를 각각 설명한다.

## P02 · 은행 계좌 이체

A에 100원, B에 40원이 있을 때 A에서 B로 30원을 이체하면 잔액은 70원과 70원이다. 다음에 80원을 요청하면 실패하며 잔액은 그대로다.

**만들 기능**　계좌마다 잔액과 mutex를 둔다. 이체는 성공 또는 실패를 돌려준다. 이 과제에서는 같은 계좌, 0 이하 금액, 잔액 부족을 실패로 정한다. 출금과 입금은 하나의 이체로 관찰되어야 한다.

### 구현 순서

1. 단일 스레드에서 정상 이체와 세 실패 사유를 구현한다.
2. 자기 이체를 먼저 판별한 뒤 서로 다른 두 계좌를 함께 잠근다. 잔액 검사부터 두 잔액 갱신까지 보호한다.
3. 여러 작업자가 반대 방향으로 이체하게 한다. 작업자별 성공·실패 수를 모아 join 후 전체 계좌를 검사한다.

### 검증

- 위 예시의 두 호출과 자기 이체·금액 0·음수 요청을 각각 검사한다. 실패 전후의 두 잔액이 같아야 한다.
- A와 B에 각각 100,000원을 두고 양방향 요청을 실행한다. 최종 총액 200,000원, 음수 잔액 0개, 성공+실패=요청 수, 제한 시간 내 종료를 확인한다.

### 벤치마크

총 100,000개 요청의 방향과 금액을 고정 시드로 미리 만든다. 같은 두 계좌에 작업자 1/2/4/8명이 요청을 나눠 실행하고 초당 이체 시도 수와 성공·실패 수를 기록한다. 실행 순서에 따라 잔액 부족 건수는 달라질 수 있다.

**완료 기준**　실패 요청이 잔액을 바꾸지 않고 양방향 실험이 총액을 보존한다. 출금 계좌부터 하나씩 잠글 때 두 작업자가 서로를 기다리는 순서를 설명한다.

## P03 · Mutex vs Atomic 비교기

이벤트 100만 개를 처리한 뒤 합계를 출력한다. 매 이벤트마다 공유 카운터를 갱신하거나, 각자 집계한 뒤 마지막에 합칠 수 있다.

**만들 기능**　mutex 증가, atomic fetch_add(기본 메모리 순서), 스레드별 로컬 합산 후 병합을 구현한다. 세 버전은 같은 이벤트를 한 번씩 센다.

### 구현 순서

1. 전체 이벤트 수 M을 먼저 정하고 N명에게 나눈다. 나머지 이벤트도 배정한다.
2. P01의 두 공유 카운터를 재사용하고, 각 스레드의 로컬 결과를 종료 시 합치는 버전을 추가한다.
3. 작업자 생성부터 종료까지의 시간과, 준비 후 집계·최종 병합까지의 시간을 구분해 기록한다.

### 검증

- M=10, N=3과 M=2, N=4에서 결과가 각각 10과 2인지 확인한다.
- 각 측정 직후 최종합=M인지 확인한다. 로컬 루프가 최적화로 단순한 산술식이 되면 그 사실을 기록하거나 실행 시 결정되는 같은 이벤트 입력을 세 구현에 사용한다.

### 벤치마크

N=1/2/4/8, M=1,000과 1,000,000을 조합한다. 각 조건에서 총 이벤트 수를 고정하고 초당 이벤트 수를 비교한다. 작은 입력에서는 작업자 준비 시간이 결과에서 차지하는 비중도 적는다.

**완료 기준**　세 버전의 최종합과 반복 측정표를 제시한다. 공유 메모리에 쓰는 횟수가 어떻게 다른지와 실제 측정 순위를 함께 설명한다.

## P04 · Spinlock과 mutex

여러 작업자가 잠금을 잡아 정수 하나를 증가시킨다. 한 버전은 atomic_flag를 반복 확인하고 다른 버전은 std::mutex를 사용한다.

**만들 기능**　lock/unlock을 가진 스핀락을 만들고 두 버전 모두 RAII 가드로 보호한다. 잠금 획득에 acquire, 해제에 release를 사용한다. 임계 구역에는 증가 연산만 둔다.

### 구현 순서

1. 한 작업자로 잠금·증가·해제 동작을 확인한다.
2. 여러 작업자가 같은 락과 카운터를 사용하게 한다. 예외로 임계 구역을 빠져나가는 테스트를 따로 만든다.
3. 잠금 클래스만 바꿔 같은 부하를 실행하는 비교 코드를 만든다.

### 검증

- N명이 R번 증가시킨 결과가 N × R이어야 한다.
- 가드 생성 뒤 예외를 던지고 잡은 다음 다른 작업자가 같은 락을 획득해 증가시킬 수 있는지 확인한다.

### 벤치마크

논리 프로세서 수를 H로 기록하고 N=1/H/2H에서 총 증가 횟수를 고정한다. 경과 시간과 프로세스 전체 CPU 시간을 함께 기록한다(Windows에서는 GetProcessTimes의 사용자+커널 시간 차). 여러 코어를 쓰면 합산 CPU 시간이 경과 시간보다 클 수 있다.

**완료 기준**　정확한 카운트와 예외 후 재획득을 확인한다. 이전 소유자의 쓰기가 다음 소유자에게 보이는 과정을 해제→획득 그림으로 표시하고, 대기 순서와 대기 상한을 보장하는지 설명한다.

## P05 · Thread-Safe Stack

7을 한 번 넣고 두 사람이 동시에 꺼내면 한 사람만 7을 받는다. 나머지 사람은 빈 결과를 받는다.

**만들 기능**　push(value)와 try_pop()을 제공한다. try_pop은 비었으면 빈 optional, 성공하면 꺼낸 값을 반환한다. 비어 있는지 확인하고 원소를 꺼내는 과정은 한 번의 잠금 안에서 수행한다.

### 구현 순서

1. 한 스레드로 1, 2를 넣고 2, 1, 빈 결과 순서로 꺼낸다.
2. 내부 원소의 소유권을 호출자에게 옮긴다. 이동 전용 값으로도 검사한다. 초급 범위에서는 이동 생성이 예외를 던지지 않는 값으로 제한해도 된다. 이 경우 타입 제약을 명시한다.
3. 고유 ID를 범위별로 나누어 생산한다. 소비자는 성공한 ID를 개인 목록에 보관한다. 생산 종료가 확인된 뒤 스택이 비면 소비자를 종료한다.

### 검증

- 원소 1개를 두 소비자가 동시에 요청해 성공 1회인지 확인한다. unique_ptr를 넣고 꺼내 소유권 전달도 확인한다.
- 모든 작업자 종료 후 성공한 push/pop ID 목록을 정렬해 대조한다. 중복·누락이 각각 0이어야 한다. 이동 예외를 허용한다면 실패 시 원소 상태를 명시하고 테스트한다.

### 벤치마크

생산자:소비자를 1:1과 4:4로 두고 각각 총 100,000개를 넣고 모두 꺼낸다. 초당 전달 원소 수와 빈 pop 시도 수를 기록한다. 소비자 종료 판단 전후에 생산 종료와 마지막 push의 순서가 보장되게 한다.

**완료 기준**　빈 스택과 동시 pop 테스트가 통과하고 두 ID 목록이 일치한다. push와 pop 각각에서 원소가 논리적으로 추가·제거되는 지점을 코드에 표시한다.

## P06 · 생산자·소비자 작업 큐

용량 2인 큐에 A, B를 넣고 닫는다. 새 항목 C는 거절되고, 소비자는 A, B를 차례로 받은 뒤 종료 신호를 받는다.

**만들 기능**　양의 용량을 가진 FIFO 큐에 push, pop, close를 만든다. 열린 큐가 가득 차면 push가 기다리고, 비면 pop이 기다린다. close는 여러 번 호출해도 같은 효과를 낸다.

### 구현 순서

1. 먼저 대기 없이 작은 입력으로 FIFO 순서와 닫힌 상태의 반환값을 확인한다.
2. 큐와 closed를 한 mutex로 보호한다. 생산자는 ‘닫혔거나 빈자리 있음’, 소비자는 ‘닫혔거나 항목 있음’을 조건 변수로 기다린다.
3. close에서 양쪽 대기자를 모두 깨운다. 먼저 생산자를 종료한 뒤 큐를 닫고, 소비자는 남은 항목을 처리한 뒤 종료하게 연결한다.

### 검증

- 용량 1인 빈 큐에서 pop 대기 중 close하면 종료 결과를 받아야 한다. 가득 찬 큐에서 push 대기 중 close하면 해당 push는 실패하고 기존 항목은 꺼낼 수 있어야 한다. 테스트용 신호로 대기 경로 진입을 확인한다.
- 생산자/소비자 수를 각각 1 또는 4로 조합한 네 경우에 고유 ID를 전달한다. 승인된 ID가 모두 한 번씩 소비되고 모든 작업자가 종료되어야 한다.

### 벤치마크

같은 총 100,000개를 처리하며 용량 1과 64를 비교한다. 생산자·소비자 수, 초당 전달 건수, 종료 시 남은 항목 수를 기록한다. 검증용 신호는 시간 측정에서 제외한다.

**완료 기준**　빈 큐와 포화 큐 양쪽에서 close가 대기자를 깨운다. 닫힌 뒤 추가 승인은 0건이고 마지막 항목까지 전달된다.

## P07 · 철학자들의 식사

원형 테이블에서 사람 i는 포크 i와 (i+1) % N을 모두 가져야 한 번 먹을 수 있다. 모두가 왼쪽 포크를 든 채 오른쪽을 기다리면 아무도 진행할 수 없다.

**만들 기능**　사람마다 작업자 하나, 포크마다 mutex 하나를 둔다. 교착을 재현하는 진단 프로그램과, 일정한 잠금 순서 또는 scoped_lock을 사용하는 정상 프로그램을 만든다.

### 구현 순서

1. N=2에서 두 사람이 차지한 포크와 기다리는 포크를 그린다.
2. 진단 전용 프로세스에서 각자 첫 포크를 잡은 다음 barrier로 전원을 맞추고 두 번째를 요청한다. 부모 테스트가 제한 시간 후 자식 프로세스를 종료·회수한다.
3. 정상 버전에서는 진단 barrier를 제거한다. 각 사람이 두 포크를 얻은 순간과 식사를 마친 횟수를 개인 기록에 남긴다.

### 검증

- 진단 버전은 전원이 첫 포크를 얻은 기록 뒤 제한 시간 안에 끝나지 않는지 확인한다.
- 정상 버전은 N=2/5/16, 1인당 1,000회로 실행한다. 각자의 식사 수=1,000, 총합=N × 1,000, 전체 종료를 확인한다.

### 벤치마크

정상 버전에서 두 포크 요청 직전부터 모두 획득할 때까지 잰다. N별 초당 식사 수와 개인별 최대 대기를 기록한다. 개인별 최댓값을 함께 보면 전체 처리량에 가려진 긴 대기를 찾을 수 있다.

**완료 기준**　진단·정상 실행의 관찰 기록을 남긴다. 서로 기다려 멈추는 교착, 한 사람만 계속 밀리는 기아, 재시도만 반복하는 라이브락을 구별하고 이번 실행에서 관찰한 범위를 적는다.

## P08 · Readers–Writers 설정 저장소

서버 설정이 (버전 1, 최대 인원 100, 틱레이트 30)에서 (버전 2, 최대 인원 200, 틱레이트 60)으로 바뀐다. 갱신과 겹친 읽기에서 허용되는 결과는 이 두 묶음이다. (2, 100, 60)이 한 번이라도 나오면 실패다.

**만들 기능**　저장소가 버전과 두 설정값을 가진 객체 하나를 소유한다. 예시 API는 Settings Read()와 void Write(int maxPlayers, int tickRate)다. Write는 배타 잠금 안에서 버전을 1 올리고 전달받은 두 값을 함께 반영한다. 호출자가 이전과 같은 값을 전달해도 된다. Read는 잠금 안에서 상태를 복사해 값으로 반환한다. 출력용 참조 매개변수는 필요 없다.

### 구현 순서

1. 초기 상태를 (0, 0, 0)으로 둔다. 먼저 mutex 하나로 Read와 Write를 보호한다. 예전 읽기 결과를 보관해 둔 채 새 값을 쓰고 다시 읽는다.
2. 같은 API의 shared_mutex 버전을 만든다. 읽기는 shared_lock, 쓰기는 배타 잠금을 쓴다. 읽기 잠금을 쥔 채 쓰기 잠금으로 승격하려는 경로를 두지 않는다.
3. 두 저장소에 같은 테스트와 부하를 적용할 수 있게 한다. 검증 실행에서는 쓰기 값의 출처를 추적하고 측정 실행에서는 호출 종류와 작업량을 통제한다.

### 검증

- Write(100, 30) 후 받은 복사본은 (1, 100, 30)이다. 이어 Write(100, 60)을 호출하면 새 결과는 (2, 100, 60)이고 앞서 받은 복사본은 그대로여야 한다.
- writer 1명이 k=1부터 100,000까지 Write(10k, 20k)를 호출하는 동안 reader 4명이 반복해 읽는다. 10k는 10 × k라는 뜻이다. 모든 결과에서 두 값이 각각 버전의 10배·20배인지 검사한다. 초기 상태도 이 식을 만족한다. 각 reader의 읽기 횟수가 양수인지, 불일치 0건인지, 마지막 버전이 100,000인지 확인한다. 이 식은 테스트 입력에만 쓰인다.

### 벤치마크

작업자 4명이 총 100,000회 호출한다. 읽기/쓰기 비율은 **완료할 호출 수** 기준으로 100:0, 90:10, 50:50을 만든다. 예를 들어 90:10이면 읽기 90,000회와 쓰기 10,000회다. 고정 시드로 목록을 섞어 분배하고 두 버전에 그대로 사용한다. 전체 호출/s를 잰다. 별도 계측 실행에서 쓰기 잠금 요청 직전부터 획득 직후까지 수집해 중앙값·p95를 적는다. 100:0의 쓰기 대기는 ‘해당 없음’이다.

**완료 기준**　두 버전 모두 복사본 유지와 일관성 검사를 통과하고 세 비율의 비교표가 있다. 읽기 공유가 어느 조건에서 도움이 되었는지와 관찰한 writer 대기를 설명한다. 특정 공정성이나 실행 순서를 전제로 합격을 판정하지 않는다.

## P09 · 주차장 관리

자리가 두 곳이면 세 번째 차량은 앞차 한 대가 나갈 때까지 기다린다. 입장 직후 차량 처리에서 예외가 발생해도 그 자리는 다음 차가 쓸 수 있어야 한다.

**만들 기능**　counting_semaphore를 용량 C로 시작한다. 입장마다 허가 하나를 얻고 퇴장마다 하나를 돌려준다. 허가의 수명을 RAII 객체로 표현한다. 현재 점유·최대 점유 통계는 별도 동기화로 관리한다.

### 구현 순서

1. C=1에서 입장→퇴장→재입장을 구현한다. 허가를 얻은 뒤에만 반환 책임을 갖고 중복 반환을 막는다.
2. 정상·예외 경로 모두 점유 감소 후 허가를 반환하게 한다. 예외는 작업자 내부에서 받아 결과로 남긴다.
3. 여러 차량을 출발시키고 입장 전후 대기 시간과 점유를 기록한다. 통계용 잠금은 주차 시간 동안 쥐고 있지 않는다.

### 검증

- C=1에서 첫 차량 입장 후 예외를 발생시킨다. 첫 차량이 빠져나가면 다음 차량의 입장이 성공해야 한다.
- C=1/4/16에서 항상 0 ≤ 점유 ≤ C, 종료 시 점유=0인지 확인한다. 전원이 나간 뒤 C개의 허가를 동시에 보유할 수 있는지도 검사한다.

### 벤치마크

32개 작업자가 총 3,200번 입장을 시도하고 입장당 약 1ms 머문다고 정한다. C별 초당 완료 방문 수, 입장 대기 p95, 최대 점유를 적는다. 실제 대기에는 운영체제 스케줄링 시간도 포함된다.

**완료 기준**　용량 상한을 한 번도 넘지 않고 예외 후 재입장과 전체 허가 회수가 성공한다.

## P10 · 동시 실행 제한 작업 관리자

작업자 8명이 요청 100개를 받는다. 외부 서비스를 동시에 호출할 수 있는 수가 2라면 세 번째 호출은 허가가 생길 때까지 기다려야 한다.

**만들 기능**　고정 개수의 작업자가 큐에서 작업을 꺼내고 외부 작업 구간에 들어가기 전에 permit을 얻는다. 제출자는 future로 각 작업의 결과나 예외를 받는다. active는 허가를 얻고 외부 구간에서 실행 중인 수다.

### 구현 순서

1. 작업 1개를 제출하고 future에서 결과를 받는다. 이어 예외를 던지는 작업도 제출해 해당 future로 실패가 전달되는지 본다.
2. P06의 큐와 P09의 허가 반환 방식을 연결한다. 실패한 작업 뒤에도 작업자 루프가 다음 요청을 받게 한다.
3. 제출 종료 후 큐를 닫고 승인된 작업을 끝낸 뒤 모든 작업자를 join한다. 큐 길이와 active 값을 시각과 함께 기록하는 계측 모드를 둔다.

### 검증

- 작업자 8명, 제한 2에서 100개 중 ID가 10의 배수인 작업을 실패시킨다(ID 0~99). future 100개가 모두 완료되고 성공 90, 실패 10인지 확인한다.
- 최대 active ≤ 2, 종료 시 active와 큐 길이 모두 0인지 확인한다. 이미 큐에서 꺼내 허가를 기다리는 작업자는 두 수치 어디에도 포함되지 않는다.

### 벤치마크

같은 작업 목록에서 짝수 ID는 1ms, 홀수는 5ms 외부 작업을 흉내 낸다. 제한 1/2/4, 작업자 8명을 고정해 초당 완료 수(성공+실패)를 비교한다. 별도 실행에서 시간축에 큐 길이와 active를 그려 제출 직후와 종료 직전의 차이를 본다.

**완료 기준**　모든 future가 성공값 또는 예외에 도달하고 실패 후 자원이 회수된다. 제한별 처리량 표와 큐 길이·active 그래프가 있다.

## P11 · 비동기 로그 시스템

여러 생산자가 Log(id, text)를 호출하면 백그라운드 writer 한 명이 파일에 한 줄씩 기록한다. 마지막 호출 직후 종료를 요청해도 이미 승인된 로그의 처리 결과를 확인할 수 있어야 한다.

**만들 기능**　P06의 용량 제한 큐를 재사용한다. 이 과제의 기본 정책은 포화 시 대기다. 거절 정책을 선택해도 되며 포화 시 호출 결과를 문서화한다. Log의 승인은 큐에 들어갔다는 뜻이다. Close는 새 승인을 중단하고 남은 항목을 처리한 뒤 flush·파일 닫기·writer join까지 마친다.

### 구현 순서

1. 일단 동기 방식으로 고유 ID와 본문을 한 줄로 기록하고 파일에서 다시 읽는다.
2. 파일을 연 뒤 writer를 시작한다. 생산자는 큐에 넣고 writer만 파일에 쓴다. 시작 시 파일 열기가 실패하면 시작 실패를 반환하고 승인을 받지 않는다.
3. 닫힌 큐 때문에 깨어난 생산자에게 거절을 돌려준다. 쓰기·flush 실패를 호출 결과나 종료 보고서에 남긴다. 단순한 구현은 flush로 성공을 확인한 배치만 written으로 세고, 확인되지 않은 배치는 failed로 분류할 수 있다. failed는 디스크에 없다고 확정했다는 뜻이 아니다.

### 검증

- 생산자 4명이 중복 없는 ID를 제출한다. 정상 종료 후 파일을 다시 읽어 승인 ID와 파일 ID를 대조한다. 누락·중복 0건, 승인=기록 성공이어야 한다.
- 용량 1과 느린 writer로 포화를 만든 뒤 종료를 요청한다. 대기 중인 생산자와 writer가 끝나고 종료 뒤 Log는 거절되어야 한다. 파일 열기 실패와 실행 중 쓰기 실패를 따로 유도해 승인=written+failed, 시도=승인+거절을 확인한다.

### 벤치마크

동기 기준은 생산자가 같은 파일을 mutex로 보호해 직접 쓰게 한다. 두 방식에 같은 ID·본문·생산자 수·flush 정책을 적용한다. 기본 입력은 생산자 4명, 총 40,000줄이다. 호출 지연 p95와 첫 제출부터 최종 flush·닫기까지의 초당 기록 성공 수를 따로 적는다. 거절 정책이면 거절 수도 표에 넣는다.

**완료 기준**　파일 대조, 실패 집계, 종료 후 writer 회수를 확인한다. 파일에 적용되는 순서 보장 범위(예: 큐에 들어간 순서)를 설명하고 호출 지연과 전체 기록 시간의 차이를 측정값으로 해석한다.
