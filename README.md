## 이 문서의 역할

필수 17개 프로젝트 이후에 선택할 수 있는 심화·응용 주제를 정리한다. 지금 모든 항목의 세부 일정이나 의무 완료 기준을 확정하지 않는다. 중급까지 해본 뒤 관심 분야와 부족한 개념을 기준으로 한 갈래씩 선택한다.

새로운 고급 프로젝트를 정할 때는 프로젝트당 2~3주 범위에 맞춰 최소 기능을 다시 정한다. 아래 갈래 전체를 2~3주에 끝낸다는 뜻은 아니다. 메모리 회수·할당기·네트워크처럼 추가 기반 지식이 필요한 항목은 준비 실습과 구현을 분리해야 한다.

## 선택 1 · 메모리 모델과 동시성 컨테이너

> **추천 대상** · atomic이 일반 데이터를 언제 안전하게 공개하는지 이해하고 싶은 경우.

**권장 흐름:** 게시·관찰의 happens-before 연습 → 정수 전용 SPSC 링 버퍼 → 스핀 대기와 blocking 비교 → 필요하면 lock-free 자료구조와 메모리 회수.

| 항목 | 기존 원본 | 범위와 주의점 |
|---|---|---|
| 잠금 기반 연결 리스트 | P13 | lock coupling과 삭제 중 객체 수명. 전체 잠금 기준을 유지 |
| SPSC 링 버퍼 | P14 | 생산자 1개·소비자 1개, 고정 용량, 정수 타입부터 시작 |
| Spinlock | P04 | atomic_flag·acquire/release의 의미와 CPU 소모를 함께 분석 |
| Lock-Free Stack | P15 | CAS뿐 아니라 ABA·노드 수명·안전한 회수까지 별도 분석 |
| Lock-Free Queue | P16 | 검증된 알고리즘 명세를 선택하고 helping·dummy·회수 가정 설명 |
| MPMC Bounded Queue | P17 | 슬롯 예약·게시·재사용과 진행 보장을 구분 |
| 큐 비교 실험 | P46 | 각 구현이 지원하는 생산자·소비자 조합에서만 비교 |

### 첫 프로젝트 후보

SPSC 큐의 순서·누락·중복·인덱스 순환 검증. 기본 메모리 순서로 시작해 release/acquire의 필요 관계를 설명한 뒤 비교한다. 생산자의 원소 게시뿐 아니라 소비자의 슬롯 반환도 분석한다.

심화 실습인 SPSC의 패딩·batching·대기 전략 비교는 기본 구현 완료 후 추가한다. atomic을 사용했다는 사실만으로 전체 연산이 lock-free라고 주장하지 않는다.

## 선택 2 · 스케줄링과 반복 계산

> **추천 대상** · 같은 worker 수에서 작업 분배를 개선하거나 단계 동기화를 더 깊이 이해하고 싶은 경우.

| 항목 | 기존 원본 | 범위와 주의점 |
|---|---|---|
| 정책 스케줄러 시뮬레이터 | P24 | 가상 시계의 FIFO·우선순위·round-robin과 실제 실행을 구분 |
| Work-Stealing Scheduler | P26 | M01·M07 확장. 처음에는 worker별 deque를 mutex로 보호 |
| 병렬 격자 시뮬레이터 | 추가 주제 | M05의 barrier·이중 버퍼를 생명 게임 등으로 확장 |

### 첫 프로젝트 후보

잠금 기반 작업 훔치기. 균등 부하·한 worker에 몰린 부하·작은 작업 다수를 비교하고, 중복·누락·마지막 원소 경쟁·유휴 대기·전체 종료를 검증한다.

원본 P26에 고급 큐 선행 조건이 있었지만, 잠금 기반 첫 구현에 lock-free 큐 완성은 필수가 아니다. 고급 deque로 교체하는 것은 별도 확장이다.

## 선택 4 · 비동기 시스템과 네트워크

| 항목 | 기존 원본 | 배우는 문제 |

| 채팅 서버 | P35 | 메시지 경계·방송·느린 수신자·종료 |

### 첫 프로젝트 후보

파일 기반 리소스 로더 또는 로컬 Echo 서버. 네트워크를 선택한다면 TCP 스트림·부분 송수신·사용할 I/O 라이브러리를 먼저 익힌다. C++20 표준 스레드 라이브러리만으로 네트워크 학습 전체가 해결되는 것은 아니다.

blocking I/O를 다른 스레드에 맡기는 방식과 OS 비동기 I/O를 구분한다. 스레드 풀과 이벤트 루프의 역할을 혼동하지 않는다. 범용 HTTP 서버·인증·배포까지 한 프로젝트에 묶지 않는다.

## 선택 5 · 성능·메모리 관리

> **추천 대상** · 동작하는 프로그램에서 실제로 관찰한 병목을 더 분석하고 싶은 경우.

| 항목 | 기존 원본 | 배우는 문제 |
|---|---|---|
| False Sharing | P41 | 독립된 쓰기의 캐시 경합·패딩 비용 |
| Mutex vs Atomic 경합 심화 | P42 | 작업량·핫키·분할·batching의 상호작용 |
| Spin vs Blocking | P43 | 선점·과도한 스핀·CPU 시간·대기 지연 |
| Thread-Local Memory Pool | P44 | 로컬 할당·해제 소유권·종료 회수 |
| 제한된 메모리 할당기 | P45 | size class·원격 해제·예약 메모리·단편화 |
| NUMA | P47 | 실제 노드·실행 위치·메모리 위치·장비 제약 |

### 첫 프로젝트 후보

B02 카운터 또는 SPSC 인덱스의 배치 변경 실험. 연산·메모리 순서·작업량을 고정한 채 배치만 바꾸고 메모리 비용도 기록한다. 성능 차이가 없으면 그 결과를 그대로 분석한다.

atomic::wait/notify는 별도의 대기 전략 실습으로 추가할 수 있다. 값의 변화·대기 조건·깨우기·종료 규칙을 먼저 정하고 바쁜 대기·조건 변수와 같은 계약으로 비교한다. notify만 호출하면 종료가 해결된다고 가정하지 않는다.

NUMA 실험은 실제 장비가 지원할 때 수행한다. 지원하지 않으면 실험 설계와 제한을 기록하고 원격 접근 측정값을 만들지 않는다.

## 선택 6 · 최종 통합과 최적화

원본 P48의 게임·서버 전체 통합은 장기 선택 목표다. 모든 원본 항목을 완료해야 시작할 필요는 없다. 이미 만든 모듈 중 필요한 것만 선택해 통합한다.

1. 고정 입력을 재생하는 기준 버전을 보존한다.
2. 결과·수명·실패·종료를 먼저 검증한다.
3. 가장 큰 병목 하나를 측정으로 찾는다.
4. 변경 하나씩 적용하고 동일 조건으로 비교한다.
5. 성능 악화나 복잡도 증가가 이득보다 크면 되돌리고 이유를 남긴다.

## 선택할 때의 기준

- 메모리 순서가 궁금하다면 SPSC부터 시작한다.
- worker별 작업량이 심하게 다르면 작업 훔치기를 검토한다.
- 시각적인 결과물이 동기 부여가 된다면 파티클·레이트레이서를 고른다.
- 서비스 개발에 관심이 있다면 리소스 로더·Echo 서버를 고른다.
- 이미 성능 문제를 관찰했다면 해당 병목을 설명하는 실험을 먼저 고른다.

선택한 프로젝트의 범위와 선수 지식을 확인한 뒤 2~3주 계획을 별도로 잡는다. 필수 과정의 정확성·수명·종료·측정 규칙은 고급에서도 그대로 유지한다.
