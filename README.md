## 과정 목표

초급에서 만든 큐·작업자·결과 전달을 재사용해 스레드 풀을 만든다. 파일 검색·정렬·이미지 처리에 적용하고, 여러 단계의 흐름과 작업 의존성을 다룬다. 마지막 결과물은 정적 DAG를 실행하는 미니 Job System과 이미지 처리 데모다.

모든 프로젝트는 가장 단순한 올바른 기준 구현을 유지한다. 잠금 없는 구현이나 최대 성능을 통과 조건으로 삼지 않는다. 기존 파일의 수명·실패·종료 검증은 유지하되, 일정에 맞게 지원 기능을 제한한다.

## M01 · 결과를 반환하는 스레드 풀

> **학습 목표**
>
> 스레드를 재사용하면서 결과·예외·종료를 하나의 실행 구조로 묶는다.

| 항목 | 내용 |
|---|---|
| 권장 기간 | **10일** · 하루 2~3시간 |
| 선행 프로젝트 | [B05](MTH_BeginnerProject.md#b05)·[B08](MTH_BeginnerProject.md#b08)·[B09](MTH_BeginnerProject.md#b09) |
| 핵심 도구·개념 | workers, `packaged_task`, `future`, 접수·종료 상태 |

### 필수 구현

- 생성 시 정한 수의 작업 스레드와 잠금 기반 작업 큐.
- `submit`으로 작업을 접수하고 `future` 반환. `packaged_task` 등으로 작업 예외 전달.
- 상태는 접수 가능 → 종료 중 → 종료 완료. 종료와 `submit`이 경쟁할 때 접수 여부를 한 동기화 규칙으로 결정.
- 종료 중 새 제출은 명확히 거절. 이미 접수한 작업은 모두 처리한 뒤 합류하는 drain 정책.
- move-only인 `packaged_task`를 C++20에서 저장할 방법을 명시. 필요하면 `shared_ptr`로 감싼 callable을 사용하고 그 수명·비용을 설명.
- 풀 내부 작업에서 같은 풀의 다른 `future`를 기다리는 사용은 지원하지 않음. 풀 종료·파괴도 소유 측 스레드에서 수행.

### 진행 계획

| 일정 | 할 일 |
|---|---|
| 1~2일차 | 상태·접수 계약, 결과 없는 고정 worker와 큐. |
| 3~5일차 | `submit`·`future`·예외 전달. |
| 6~8일차 | 종료 경쟁·반복 생성/파괴·실패 검증. |
| 9~10일차 | 작업 크기별 비교와 문서 정리. |

### 검증 체크리스트

- [ ] worker 1개, 작업 0개, 정상·예외 작업 혼합, 종료와 `submit` 경쟁, 종료 반복.
- [ ] worker 0개 입력 정책을 정한다.
- [ ] 접수된 모든 작업은 정확히 한 번 실행되고, 모든 `future`가 값 또는 예외를 받는지 확인한다.
- [ ] 거절된 작업은 접수 수에 포함하지 않는다.

### 벤치마크

- 순차·작업마다 `thread` 생성·스레드 풀을 같은 작업량으로 비교.
- 작은 작업·중간 작업·큰 작업별 측정.
- 풀 생성·파괴 포함 시간과 이미 생성된 풀의 반복 처리 시간을 분리한다.
- B08의 `async` 비교는 제한된 작업 수에서 추가할 수 있다.

### 완료 기준

- [ ] 접수 = 성공 + 실패
- [ ] 중복 실행 0
- [ ] 모든 `future` 완료
- [ ] 모든 worker 합류.
- [ ] 작은 작업에서 관리 비용이 커지는 이유를 설명한다.

<details>
<summary>선택 확장 · 원본 연결 펼치기</summary>

- 제한 큐와 제출 backpressure, 미실행 작업 취소.
- 실행 중 강제 중단은 구현하지 않는다.

**원본 연결**

P23을 중급 첫 과제로 이동. P10·P19에 흩어져 있던 실행 관리와 결과 전달을 흡수. 일반적인 잠금 큐로 완성할 수 있다.

</details>

## M02 · 잠금을 분할한 인메모리 저장소

> **학습 목표**
>
> 잠금의 범위와 데이터 배치가 경합에 미치는 영향을 관찰한다.

| 항목 | 내용 |
|---|---|
| 권장 기간 | **8일** · 하루 2~3시간 |
| 선행 프로젝트 | [B04](MTH_BeginnerProject.md#b04)·[B06](MTH_BeginnerProject.md#b06), [M01](#m01)의 부하 실행기 |
| 핵심 도구·개념 | sharding, `shared_mutex`, 값 반환 |

### 필수 구현

- `get`·`put`·`erase`. `get`은 값의 복사본 또는 `optional`을 반환.
- 전체 `mutex` 버전, 전체 `shared_mutex` 버전, 고정 개수의 독립 맵과 잠금을 가진 분할 버전.
- 키를 해시해 하나의 분할에 배정. 실행 중 분할 개수 변경은 제외.
- 하나의 `unordered_map`을 여러 독립 잠금으로 무작정 보호하지 않음. 각 맵의 구조 변경은 해당 맵의 잠금으로 보호.
- 전체 크기는 작업 종료 후 정확히 확인. 실행 중 정확한 전체 스냅샷은 선택.

### 진행 계획

| 일정 | 할 일 |
|---|---|
| 1~2일차 | API·전체 잠금 |
| 3~4일차 | 읽기 잠금·분할 |
| 5~6일차 | 경쟁 검증 |
| 7~8일차 | 부하별 측정. |

### 검증 체크리스트

- [ ] 같은 키의 갱신·조회·삭제 경쟁, 서로 다른 분할의 동시 작업, 빈 맵, 키 중복.
- [ ] 값에 버전과 관계식을 넣어 잘못 섞인 결과를 검사한다.
- [ ] 같은 키의 경쟁 갱신은 실행 순서가 달라질 수 있으므로 최종값 하나만 고정된 기대값과 비교하지 않는다.
- [ ] 작은 호출·반환 이력은 순차 API 규칙과 대조한다.

### 벤치마크

- 읽기:쓰기 100:0·90:10·50:50, 균등 키·핫키 분포, 분할 수 변화.
- 같은 요청량과 성공·실패 집계 기준 사용.
- 읽기 처리량뿐 아니라 writer 대기도 확인.

### 완료 기준

- [ ] 내부 참조 유출 없음
- [ ] 키별 정합성·종료 확인
- [ ] 분할이 도움이 되는 조건과 핫키에서 효과가 제한되는 이유 설명.

<details>
<summary>선택 확장 · 원본 연결 펼치기</summary>

- 모든 분할을 정해진 순서로 잠그는 정확한 스냅샷, 크기·일관성 계약 비교.
- LRU·만료·디스크 저장은 제외.

**원본 연결**

P12 유지. B06은 단일 객체의 일관성, M02는 여러 키의 경합 분산을 다룬다.

</details>

## M03 · 병렬 파일 검색기

> **학습 목표**
>
> 같은 실행 기반을 실제 I/O 작업에 적용하고 저장 장치·캐시의 영향을 구분한다.

| 항목 | 내용 |
|---|---|
| 권장 기간 | **7일** · 하루 2~3시간 |
| 선행 프로젝트 | [M01](#m01) |
| 핵심 도구·개념 | filesystem, 파일별 작업 분할, 결과·오류 수집 |

### 필수 구현

- 지정 폴더의 파일 목록을 먼저 수집한 뒤 파일별 검색 작업을 M01에 제출.
- 지원 확장자와 검색 문자열을 지정하고 파일·행 등 정해진 결과 형식으로 반환.
- 입력은 생성한 텍스트 파일로 시작. 인코딩·대소문자·줄바꿈·바이너리 파일 정책 명시.
- 디렉터리 심볼릭 링크는 기본적으로 따라가지 않음. 열거 오류·파일 열기 실패·읽기 실패를 결과와 분리.
- 결과는 작업별 로컬 저장 후 호출 측에서 병합. 출력 순서는 별도 정렬로 결정.

### 진행 계획

| 일정 | 할 일 |
|---|---|
| 1~2일차 | 고정 테스트 폴더·순차 검색 |
| 3~4일차 | 풀 실행·병합 |
| 5일차 | 실패 검증 |
| 6~7일차 | 측정. |

### 검증 체크리스트

- [ ] 빈 폴더, 빈 파일, 검색 결과 없음, 여러 일치, 삭제된 파일, 접근 실패.
- [ ] 읽기 전용 고정 입력에서는 순차 결과 집합과 일치해야 한다.
- [ ] 실행 중 파일 변경까지 일관된 스냅샷으로 보장하지 않는다고 명시한다.

### 벤치마크

- 작은 파일 다수와 큰 파일 소수, worker 수 변화.
- 목록 열거·검색·결과 정렬 시간을 분리한다.
- warm-cache 반복을 명시하고, OS 캐시를 통제하지 않았다면 cold-cache 성능이라고 주장하지 않는다.

### 완료 기준

- [ ] 결과 집합 일치
- [ ] 오류 항목 보고
- [ ] 접수 작업 전부 완료
- [ ] 스토리지 병목 때문에 느려진 경우도 설명.

<details>
<summary>선택 확장 · 원본 연결 펼치기</summary>

- 탐색 중 검색 작업 생성, 제한된 미완료 작업 수, 협력적 취소.
- 동적 탐색을 추가할 때는 빈 큐와 탐색 완료를 구분한다.

**원본 연결**

P18 유지. 풀을 먼저 배웠으므로 실행 backend를 나중에 교체하는 단계를 생략한다.

</details>

## M04 · 병렬 병합 정렬

> **학습 목표**
>
> 계산량·추가 메모리·작업 관리 비용의 균형을 찾는다.

| 항목 | 내용 |
|---|---|
| 권장 기간 | **8일** · 하루 2~3시간 |
| 선행 프로젝트 | [M01](#m01), 순차 병합 정렬 이해 |
| 핵심 도구·개념 | 구간 분할, 단계별 의존성, 작업 크기 |

### 필수 구현

- 순차 병합 정렬과 병렬 버전. 정렬 안정성을 보장할지 먼저 명시.
- 고정 크기 구간들을 병렬로 정렬하고, 병합 단계마다 겹치지 않는 출력 구간을 각 작업에 배정.
- 단계 완료 대기는 호출 측에서 수행하고 다음 병합 단계 제출. 풀 worker가 같은 풀의 하위 작업을 기다리지 않음.
- 입력·출력 보조 버퍼의 역할을 단계별로 정하고 동시에 읽는 영역을 덮어쓰지 않음.
- 작은 구간은 순차 처리. 불필요한 복사·할당을 어디에 포함했는지 기록.

### 진행 계획

| 일정 | 할 일 |
|---|---|
| 1~2일차 | 순차 기준 |
| 3~4일차 | 구간 정렬·단계별 병합 |
| 5~6일차 | 경계·안정성 |
| 7~8일차 | cutoff·메모리 비교. |

### 검증 체크리스트

- [ ] 빈 배열, 원소 1개, 홀수 길이, 정렬·역순·랜덤·중복 입력.
- [ ] 안정성을 보장한다면 키와 원래 위치를 함께 저장해 같은 키의 순서를 검사한다.
- [ ] 요소 누락·중복도 확인한다.

### 벤치마크

- 같은 병합 정렬의 순차·병렬 비교를 주 기준으로 사용.
- 표준 정렬 함수는 별도 기준으로 비교해 알고리즘 차이와 스레드 효과를 혼동하지 않는다.
- 입력 크기·구간 크기·worker 수와 추가 메모리를 기록.

### 완료 기준

- [ ] 정렬·원소 보존·선언한 안정성 계약 충족
- [ ] 무제한 스레드 생성 없음
- [ ] 작은 작업에서 손해가 나는 이유 설명.

<details>
<summary>선택 확장 · 원본 연결 펼치기</summary>

- 하나의 큰 병합 자체를 병렬화.
- 재귀적 fork/`join`은 이를 지원하는 실행 구조를 따로 설계한 뒤 수행.

**원본 연결**

P19 유지. 단순 풀에서의 종속 `future` 대기 문제를 기본 설계에서 피한다.

</details>

## M05 · 병렬 이미지 필터와 반복 처리

> **학습 목표**
>
> 공유 쓰기를 줄이는 데이터 분할과 반복 계산의 단계 동기화를 익힌다.

| 항목 | 내용 |
|---|---|
| 권장 기간 | **8일** · 하루 2~3시간 |
| 선행 프로젝트 | [M01](#m01)·[M04](#m04) |
| 핵심 도구·개념 | 데이터 분할, 이중 버퍼, `barrier` |

### 필수 구현

- 명암 변환·반전·블러의 순차 기준. 생성한 이미지 또는 간단한 PPM 파일 사용.
- M01 풀로 행 또는 타일 작업을 실행. 각 출력 픽셀의 writer는 하나로 지정.
- 블러 입력·출력 버퍼 분리, 경계 처리·반올림·오차 정책 고정.
- 반복 블러는 별도 고정 worker 집합과 C++20 `barrier`로 구현. 모든 worker가 해당 반복의 쓰기를 마친 후 다음 입력을 사용.
- 버퍼 교체는 `barrier` 완료 단계 등 동기화된 위치에서 수행. 공유 포인터 교체를 임의의 스레드가 경쟁적으로 수행하지 않음.
- 반복 횟수는 실행 전에 고정. 필요한 저장 공간은 worker 시작 전에 준비해 단계 중 예외 경로를 줄임.

### 진행 계획

| 일정 | 할 일 |
|---|---|
| 1~2일차 | 필터·경계 기준 |
| 3~4일차 | 풀 기반 행/타일 |
| 5~6일차 | 반복·`barrier` |
| 7~8일차 | 검증·측정. |

### 검증 체크리스트

- [ ] 1×1, 홀수 크기, 타일보다 작은 이미지, 빈 입력 처리.
- [ ] 매 반복 결과를 순차 버전과 비교.
- [ ] 정수는 정확히, 부동소수점은 사전에 정한 오차로 검증.
- [ ] `barrier` 대기 작업을 참가자보다 작은 풀에 제출해 교착시키지 않는다.

### 벤치마크

- 이미지 크기·타일 크기·worker 수별 계산 시간.
- 읽기·저장 시간은 분리.
- 반복마다 작업을 제출하는 방식과 전용 worker·`barrier` 방식은 같은 연산량·완료 기준으로 비교.

### 완료 기준

- [ ] 픽셀 결과·경계 처리 일치
- [ ] 다음 반복의 조기 읽기 없음
- [ ] 모든 worker 정상 합류.
- [ ] 데이터 분할과 반복 동기화의 역할을 구분한다.

<details>
<summary>선택 확장 · 원본 연결 펼치기</summary>

- SIMD on/off를 별도 축으로 비교, 타일 경계의 캐시 효과.
- 실행 중 중단을 추가한다면 모든 `barrier` 참가자의 종료 규칙부터 설계.

**원본 연결**

P22에 반복 격자 계산 요소를 작은 범위로 결합. 생명 게임 전체는 고급·응용 선택으로 남긴다.

</details>

## M06 · 용량 제한 데이터 처리 파이프라인

> **학습 목표**
>
> 여러 큐가 연결된 시스템에서 병목·대기 데이터·실패·중단을 관리한다.

| 항목 | 내용 |
|---|---|
| 권장 기간 | **10일** · 하루 2~3시간 |
| 선행 프로젝트 | [B05](MTH_BeginnerProject.md#b05)·[B07](MTH_BeginnerProject.md#b07)·[B09](MTH_BeginnerProject.md#b09), [M01](#m01) |
| 핵심 도구·개념 | 단계별 처리량, backpressure, 종료 전파 |

### 필수 구현

- 고유 ID를 가진 데이터의 입력 → 변환 → 집계 3단계. 변환은 결정론적 CPU 계산으로 시작.
- 단계별 고정 worker와 용량 제한 큐. 먼저 B05의 조건 변수 큐를 재사용.
- 뒤 단계가 느리면 앞 단계가 기다리도록 구성. 실행 중 처리량·큐 깊이·최종 상태를 기록.
- 정상 완료 시 해당 단계의 마지막 생산자가 출력 큐를 닫음. 한 worker가 끝났다는 이유로 공유 출력 큐를 일찍 닫지 않음.
- 실패·중단 시 새 접수를 멈추고 모든 관련 큐의 대기를 해제. 대기·실행 중 항목의 처리 또는 취소 정책을 명시.
- 접수된 항목을 성공·실패·취소로 정산. downstream 전달 실패로 항목이 조용히 사라지지 않음.

### 진행 계획

| 일정 | 할 일 |
|---|---|
| 1~2일차 | 순차 처리·상태 계약 |
| 3~5일차 | 단계와 제한 큐 |
| 6~8일차 | 종료·실패·중단 |
| 9~10일차 | 병목 실험. |

### 검증 체크리스트

- [ ] 느린 생산자·느린 소비자, 용량 1, 변환 예외, 입력 0개, 포화 중 중단, 단계 종료 순서.
- [ ] 접수 = 성공 + 실패 + 취소, ID 중복 없음.
- [ ] 최종 결과 순서를 보장하는지 명시하고 필요하면 ID로 정렬해 비교.

### 벤치마크

- 단계별 worker 수·큐 용량·batch 크기 변화.
- 전체 완료 시간, 처리량, 제출부터 최종 완료까지의 지연, 최대 큐 깊이.
- 큐 용량과 실행 중·batch 보유 항목을 구분해 메모리 상한을 설명한다.

### 완료 기준

- [ ] 제한된 대기 항목 수
- [ ] 모든 항목의 최종 상태
- [ ] 모든 대기와 worker 종료.
- [ ] 가장 느린 단계 외의 worker 증가가 왜 도움이 되지 않는지 설명.

<details>
<summary>선택 확장 · 원본 연결 펼치기</summary>

- 조건 변수 큐와 `counting_semaphore` 큐 비교.
- 세마포어는 슬롯 수·준비 항목 수를 관리하고 큐 구조는 별도로 보호한다.
- 세마포어 자체에는 `close`나 `stop_token` 기반 취소가 없으므로 종료 메시지, timed acquire와 상태 확인 등 명시적 전략이 필요하다.
- 단순히 가짜 permit을 풀어 종료시키지 않는다.
- 비교는 같은 종료·부하 계약을 구현한 뒤 수행한다.

**원본 연결**

P06·P10·P11의 제한·대기·종료 원칙과 단계형 파이프라인 프로젝트 결합. 세마포어 큐의 종료까지 처음부터 강제하지 않아 10일 범위를 유지한다.

</details>

## M07 · 의존성 기반 미니 Job System

> **학습 목표**
>
> 선행 작업 완료에 따라 실행 가능한 작업을 찾아 실행한다.

| 항목 | 내용 |
|---|---|
| 권장 기간 | **10일** · 하루 2~3시간 |
| 선행 프로젝트 | [M01](#m01)·[M05](#m05)·[M06](#m06), 기본 그래프 이해 |
| 핵심 도구·개념 | 정적 DAG, 준비 큐, 의존성 카운트, `latch` |

### 필수 구현

- 실행 전에 확정된 작업 목록과 의존성 간선. 잘못된 ID·중복 간선 정책을 정하고 사이클 검사.
- 선행 작업 수가 0인 작업만 실행 가능 상태로 전환. 상태와 카운트는 우선 하나의 `mutex`로 보호.
- M01 풀에서 작업 실행. 결과 데이터가 후행 작업에 공개되는 동기화 관계를 명시.
- 상태는 대기·실행 가능·실행 중·성공·실패·건너뜀. 실패 작업의 후속 작업은 실행하지 않고, 독립된 가지는 계속 실행.
- C++20 `latch`로 전체 완료 대기. 성공·실패·건너뜀 모두 정확히 한 번 최종 상태에 도달하고 `count_down`. `latch`는 한 번 실행마다 새로 생성.
- 그래프·버퍼는 해당 실행이 끝날 때까지 소유. 실행 중 그래프 수정·작업 훔치기·우선순위는 제외.
- 미니 데모: 입력 준비 → 서로 독립된 필터 두 가지 → 결합 → 결과 저장. 기준 순차 실행과 비교.

### 진행 계획

| 일정 | 할 일 |
|---|---|
| 1~2일차 | 그래프·상태·순차 실행 |
| 3~5일차 | 준비 작업과 풀 연결 |
| 6~8일차 | 실패 전파·완료 검증 |
| 9~10일차 | 이미지 데모·측정. |

### 검증 체크리스트

- [ ] 빈 그래프, 사슬, 다이아몬드, 넓은 그래프, 분리된 가지, 사이클, 중간 실패.
- [ ] 이벤트 기록으로 모든 선행 작업의 성공 완료 이후에 후행 작업이 시작했는지 확인.
- [ ] 같은 후속 작업에 여러 실패가 모여도 중복 종료·중복 `count_down`하지 않음.
- [ ] pool 접수 실패도 상태와 완료 처리에서 빠뜨리지 않는다.

### 벤치마크

- 같은 그래프의 순차 실행·worker 1개·여러 worker 비교.
- 작업 크기와 그래프 폭을 변경해 전체 시간, 관리 비용, worker별 처리량을 기록.
- 사슬처럼 의존성이 긴 입력에서 병렬화 이득이 제한되는 이유를 설명한다.

### 완료 기준

- [ ] 의존성 위반·중복 실행 없음
- [ ] 모든 작업 최종 상태
- [ ] 실패 시에도 전체 대기 종료
- [ ] 데모 결과 일치.
- [ ] 정상 실행과 실패 실행의 요약 보고서를 제출.

<details>
<summary>선택 확장 · 원본 연결 펼치기</summary>

- 실행 취소, 우선순위, profiling span.
- 작업 훔치기는 별도 선택 프로젝트로 수행.

**원본 연결**

P25를 정적 그래프·잠금 기반 실행기로 제한. P48의 통합·최적화 경험을 작은 이미지 데모에서 먼저 수행한다.

</details>
